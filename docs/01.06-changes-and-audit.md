# MMerge Vita 01.06

Built from preserved 01.05. This is a normal clean build with optional runtime captures. It has passed host checks and both ARM builds, but has **not been installed or tested on the Vita**. No new device performance capture was collected this turn. Earlier builds and symbols remain preserved. No PC sampler, dormancy, device writes, database edits or public source export were used.

## Changes

- **Spell assignment:** in the spellbook, X selects a learned spell and Triangle uses the existing Quick Spell action. The same selected spell toggles its assignment off. A status message confirms the result. The visible heading says “Triangle: set quick spell”; the editable and built-in guides give the full instructions. Character identity remains visible. Circle still inspects in menus and casts in gameplay. The actual spell service, including attack fallback, is byte-for-byte unchanged from 01.05. Assignment remains per character. Held Triangle is consumed when switching modes so it cannot also cause a jump on closing the book.
- **Gameplay FPS cap:** Graphics offers Off / 30 / 20 / 60. It applies immediately and is recorded in capture settings. Fresh default is Off; existing settings are retained. The limiter sleeps only for time remaining after normal frame work, without spinning, allocating or adding a second simulation step. It does not delay menus or paused-world overlays. Sleeping happens after the diagnostic frame ends; deliberate pacing is not mislabeled as CPU work. Frame intervals still reflect it. No cap can raise low FPS.
- **Full-screen map:** the warm composed-image cache is checked before requesting source pixels. Pan, zoom, dimensions, map name and texture eviction still invalidate it. Missing composed GPU textures now force a rebuild rather than leaving a nominally valid but undrawable cache. Indoor vector maps bypass the raster image lookup. This removes two unconditional source-texture entry-point calls on the warm outdoor path; it does not prove those calls previously decoded an image each frame.
- **Installer/artwork:** one VPK contains engine/runtime libraries, shaders, Vita UI, licenses, first-run defaults, icon, transparent logo and background. The title remains OYAM00001 and the version is 01.06. Actual VPK promotion is the next artwork-registration test; manually replacing cached files previously updated only the bubble. A read-only copy of the device database lacked LiveArea records for this title. That suggests registration trouble, not proof of one precise cause. No database rewrite or unverified promoter helper is included.
- **Separated data:** the startup check and engine prefer `ux0:data/openyamm/assets` when its engine.zip exists, otherwise retain app-folder compatibility. They select one coherent archive root and report incomplete data rather than mixing two installations. Port UI always comes from the installed VPK. Game content is excluded; the instructions link to upstream OpenYAMM. The guide distinguishes prepared OpenYAMM archives from unmodified GOG files.

Moving existing archives outside the app before reinstalling protects them from the app update. This is a manual one-time step described in READ-ME-FIRST. Settings, saves and derived caches remain in `ux0:data/openyamm`. The VPK creates defaults only when absent; the separate guide-text update is intentional. Rolling back to an older build without data-root support requires restoring the five archives to its old app assets folder from your backup.

## Map investigation: what is and is not established

`GameplayOverlayTypes.h::gameplayHudScreenFullyOccludesWorld` includes Journal. `OutdoorGameView.cpp:3554` and `IndoorGameView.cpp:1211` return before world submissions for that overlay, except an explicitly requested save/beacon preview. The normal map therefore does not draw the battle behind it. `GameSession.cpp:882–910` also gates actor AI with modal pause. `GameApplication.cpp:9122–9137` skips world update.

The shared movement entry point is still called, but the outdoor controller returns on journal-consumed/world-blocked input at `OutdoorGameplayInputController.cpp:63–70`, before movement/collision. Small housekeeping and audio/UI processing remain. It would be misleading to attribute the reported 12–18 FPS to all actors being rendered or simulated behind the map.

The identified map-cache waste is fixed in `GameplayPartyOverlayRenderer.cpp:4271`. Remaining work includes 2D drawing, labels and markers, and on indoor maps vector-line preparation. There is no map-open timing capture establishing their relative cost. Please compare a warmed map at the same battle spot; if still slow, capture a stationary map-open interval plus a pan/zoom interval. No FPS gain or saved milliseconds are claimed yet.
